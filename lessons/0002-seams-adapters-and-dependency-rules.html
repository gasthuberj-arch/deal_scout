Architecture • Lesson 0002

Seams, Adapters & Dependency Rules

Where to draw lines, when to introduce ports, and how to classify dependencies in DealScout.

Progressing Your Mission

Now that you know how to identify deep modules (Lesson 0001), the next architectural decision is where boundaries belong. This lesson gives you a disciplined decision rule for placing seams and classifying dependencies without introducing needless indirection.

1. What Is a Seam?

In software architecture, developers often throw around terms like "boundary", "layer", or "abstraction". We use Michael Feathers' precise term:

Seam: A place where you can alter behavior without editing in that place; the exact location where a module's interface lives.

An adapter is a concrete implementation that sits at a seam and satisfies the interface. For instance, in DealScout, a payment module might have a production Stripe adapter and a fast test in-memory adapter.

2. Seam Discipline: The Two-Adapter Rule

A very common trap in system design is speculative seams: creating an abstract behaviour/port "just in case we ever want to switch databases or vendors."

The Two-Adapter Rule: One adapter means a hypothetical seam. Two adapters means a real one.

If you only ever have one concrete implementation (e.g. PostgreSQL) and you don't use a stand-in for tests, do not create a generic repo port! A single-adapter seam is just indirection that drains cognitive energy.

3. The Four Dependency Categories

Before drawing a boundary or creating an adapter in DealScout, categorize what the code touches:

  1. In-process (No Seam): Pure computation, string parsing, scoring rules, and in-memory structures. Merge directly into the deep module. Never extract an adapter for pure calculation.
  2. Local-substitutable (Internal Seam): Local databases (SQLite, ETS, local disk). The test stand-in runs directly in the test suite. Keep the seam internal to the module—do not leak it into public interfaces.
  3. Remote but Owned (Port & Adapter): Services you own across a network boundary (e.g. an internal recommendation service). Define a clean port at the seam; supply an HTTP adapter in production and an in-memory adapter in test.
  4. True External (Injected Mock): Third-party APIs outside your control (e.g. Stripe, Twilio, SendGrid). Inject an adapter at the port; use a mock adapter in tests to verify edge cases and failure modes.

4. Testing Strategy: Replace, Don't Layer

When you deepen a module by collapsing shallow pass-through layers, what happens to your tests?

  • Delete the obsolete unit tests: Fine-grained tests on intermediate helper layers become friction. Delete them.
  • Test the interface: The external interface is your test surface. Tests should exercise high-leverage outcomes across the seam. When internal algorithms refactor, tests shouldn't break.
