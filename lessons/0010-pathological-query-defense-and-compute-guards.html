Systems Security • Lesson 0010

Pathological Query Defense & Compute Guards

Protecting high-throughput ingestion pipelines from ReDoS, runaway ASTs, and CPU exhaustion.

Tied to Your Mission

In DealScout, users configure flexible alert rules with keyword phrases, negative terms, and custom parameters. In an open alerting system, a single pathological query (such as a catastrophic backtracking regex or a deeply nested boolean AST) can monopolize BEAM schedulers and stall deal ingestion for all users. This lesson covers how DealScout.Alerts.ComputeGuard defends the pipeline.

1. The Vulnerability: Regular Expression Denial of Service (ReDoS)

Many systems allow users to match text using patterns or wildcards. Consider what happens when an alert rule compiles an unconstrained or nested quantifier pattern against an incoming deal text:

Pathological Pattern:  (a+)+$
Target Deal Text:      "aaaaaaaaaaaaaaaaaaaaaaaaaaaaab"

Because every a can belong to either the inner or outer repetition, a naive NFA engine attempts $2^{30}$ (over one billion) state transitions before rejecting the match. A single deal evaluation can lock up a CPU core for tens of seconds.

2. Architectural Defense 1: Bounded AST Compilation

DealScout never exposes raw, user-supplied regexes directly to the matching engine. In DealScout.KeywordEngine.Query:

  • Structured AST Grammar: User inputs are parsed into a restricted Abstract Syntax Tree (AST) supporting only conjunctions, disjunctions, and literal exclusions (e.g. +rtx +4090 -laptop).
  • Recursion Depth Limiting: The parser enforces a maximum nesting depth to prevent stack exhaustion attacks.
  • Literal Token Extraction: Patterns are reduced to exact literal strings fed into an Aho-Corasick automaton, completely bypassing backtracking regex engines during candidate prefiltering.

3. Architectural Defense 2: Runtime Microsecond Budgets

Even with prefiltering, evaluation functions must execute arbitrary predicate checks (price conversions, temperature thresholds, merchant filters). DealScout.Alerts.ComputeGuard wraps rule evaluation inside an active budget boundary:

DealScout.Alerts.ComputeGuard.run(rule, deals, opts, eval_fun)
┌────────────────────────────────────────────────────────┐
│ 1. Record Monotonic Start Time:                        │
│    start = System.monotonic_time(:microsecond)        │
│ 2. Execute Rule Predicate:                             │
│    matched = eval_fun.()                               │
│ 3. Calculate Normalized Duration:                      │
│    normalized_us = div(elapsed_us, length(deals))      │
│ 4. Threshold & Budget Checks:                          │
│    - If elapsed_us > 5,000µs: Log to NDJSON slow log   │
│    - If normalized_us > 30,000µs: Trigger Auto-Pause   │
└────────────────────────────────────────────────────────┘

4. The Auto-Pause Circuit Breaker

If an alert rule exceeds its per-deal budget (default 30,000µs), ComputeGuard halts the hazard automatically:

  1. State Transition: The rule's database record is updated to is_active = false with a recorded reason (auto_paused_over_budget).
  2. Cache Eviction: The keyword engine's compiled index is marked dirty (KeywordEngine.mark_dirty()), expelling the rule from memory.
  3. Live Notification: A broadcast event ({:rule_auto_paused, rule, reason}) alerts the user in the UI, explaining why their rule was paused without taking down the pipeline for everyone else.
