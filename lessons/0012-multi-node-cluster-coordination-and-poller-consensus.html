Distributed Systems • Lesson 0012

Multi-Node Cluster Coordination & Poller Consensus

Solving duplicate polling collisions, leader election, and work partitioning across BEAM clusters.

Tied to Your Mission

When running DealScout in production across multiple instances (e.g. Fly.io, Kubernetes, or multi-host nodes), each node starts an identical supervision tree by default. If left uncoordinated, every node polls every feed simultaneously—multiplying traffic, triggering instant HTTP 429 bans, and racing on database writes. This lesson explains how to coordinate background pollers in distributed Elixir.

1. The Distributed Duplication Problem

In a single-node deployment, DealScout.Feeds.Poller maintains a queue, enforces a 2-second stagger, and handles backoff smoothly. But consider a 3-node cluster:

Node A (FRA) ───► GET https://www.pepper.com/rss/all ──┐
Node B (AMS) ───► GET https://www.pepper.com/rss/all ──┼──► 429 / 403 WAF BAN!
Node C (WAW) ───► GET https://www.pepper.com/rss/all ──┘

Each node thinks it is following polite 2-second staggering rules, but upstream servers see 3x or 10x concurrent bursts from our infrastructure.

2. Strategy 1: Database Advisory Locks (Zero Split-Brain)

When nodes share a PostgreSQL database, Postgres provides an elegant distributed mutex: Session-level Advisory Locks:

# Attempt to acquire a non-blocking 64-bit advisory lock for feed polling:
SELECT pg_try_advisory_lock(1001);
# Returns true if acquired, false if another node is currently polling.
  • Automatic Cleanup on Crash: If the worker process or node crashes, the database connection terminates, and PostgreSQL automatically releases the advisory lock immediately.
  • Split-Brain Immunity: Unlike distributed consensus algorithms operating across flaky networks, the database is the authoritative single source of truth.

3. Strategy 2: BEAM Native Global Registration (`:global`)

Erlang provides built-in distributed process registration. Instead of registering the poller locally with name: __MODULE__, you register globally:

GenServer.start_link(__MODULE__, opts, name: {:global, DealScout.Feeds.Poller})

Across the entire connected cluster of BEAM nodes, only one singleton instance runs. If the active node crashes, the supervisor on another node detects the absence and starts a replacement. However, during network netsplits, both partitions may elect a leader unless partition arbitration is configured.

4. Strategy 3: Horizontal Work Partitioning via Consistent Hashing

Singleton leader election forces one node to do 100% of the work while four other nodes sit idle. A more scalable pattern partitions feeds across active cluster members using consistent hashing:

# Inside each node's poller loop:
live_nodes = Enum.sort(Node.list([:this, :visible]))
node_index = Enum.find_index(live_nodes, &(&1 == Node.self()))
total_nodes = length(live_nodes)

# Each node only polls feeds matching its hash partition:
def should_poll_feed?(feed_id, node_index, total_nodes) do
  rem(:erlang.phash2(feed_id), total_nodes) == node_index
end

If you have 100 feeds and 4 cluster nodes, each node handles exactly 25 feeds. When a node dies or a new node joins, ownership redistributes predictably with minimal re-shuffling.
