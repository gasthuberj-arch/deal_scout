Systems Engineering • Lesson 0009

Distributed Resilience & Rate-Limiting

Architecting scrapers and background pollers that survive WAFs, 429 throttling, and memory leaks.

Tied to Your Mission

DealScout depends on external data sources (Pepper feeds, RSS, merchant APIs). If our poller bursts, crashes on dirty payloads, or gets IP-banned by Cloudflare, deal flow stops completely. This lesson formalizes the resilience primitives built into DealScout.Feeds.Poller.

1. The Anatomy of Feed Polling Hazards

Background ingestion pipelines face three primary operational hazards:

  1. Synchronized Herd Bursts: When multiple pollers or scheduled cron jobs wake up at the exact same second (e.g. every minute at :00), they slam target servers with concurrent requests, instantly triggering HTTP 429 (Too Many Requests).
  2. IP Reputation Blacklisting: Blasting an external merchant during a Cloudflare challenge or receiving repeated HTTP 403 (Forbidden) responses degrades server IP reputation and results in permanent network blacklisting.
  3. Binary Heap Bloat: Parsing multi-megabyte XML or JSON feeds inside a long-lived GenServer leaves large binary reference-counted (refc) chunks in process memory, causing silent memory leaks.

2. Solution 1: Ephemeral Worker Isolation

In Elixir, long-lived GenServers that hold state should never directly parse large network payloads. Instead, DealScout delegates the network fetch and XML parsing to an ephemeral task supervised under DealScout.Feeds.TaskSupervisor:

DealScout.Feeds.Poller (Long-lived GenServer)
    │
    ▼ (Spawns Task via Task.Supervisor)
┌────────────────────────────────────────────────────────┐
│  Ephemeral Task Process                                │
│  - Downloads HTTP stream via Req with conditional ETag │
│  - Parses XML DOM / JSON entities                     │
│  - Writes normalized deals into Ecto Repo             │
└────────────────────────────────────────────────────────┘
    │
    ▼ (Task process terminates immediately)
Erlang VM reclaims all refc binaries and heap garbage instantly!

3. Solution 2: Request Staggering & Conditional GETs

Instead of requesting all 15 feeds simultaneously in parallel, DealScout uses leaky-bucket staggering:

  • Sequential Stagger Interval: Feeds are scheduled sequentially with a mandatory inter-request delay (@min_stagger_ms 2_000). Requests appear as a gentle, human-like trickle rather than an automated DDoS attack.
  • Conditional HTTP Caching: Every outgoing request transmits If-None-Match (ETag) and If-Modified-Since headers. When feeds have no new deals, servers reply with 304 Not Modified. Zero XML parsing, zero database writes, zero wasted bandwidth.

4. Solution 3: Differentiated Backoff & Jitter

Not all errors are equal. DealScout enforces differentiated backoff strategies based on HTTP response semantics:

HTTP Error Classification Matrix:
┌──────────────┬───────────────────────────┬────────────────────────────────────────┐
│ Status Code  │ Root Cause                │ DealScout Backoff Strategy             │
├──────────────┼───────────────────────────┼────────────────────────────────────────┤
│ 429          │ Rate limit / Throttling   │ Honor Retry-After header or 5m..2h exp │
│ 403          │ Cloudflare / WAF block    │ Immediate aggressive 30m+ cooldown     │
│ 500 / 502    │ Remote server error       │ Mild backoff after 2 consecutive fails │
│ 304          │ Not modified (Success)    │ Reset error counter to 0 immediately   │
└──────────────┴───────────────────────────┴────────────────────────────────────────┘

Why Exponential Backoff Needs Jitter

Standard exponential backoff ($2^n$) has a fatal flaw: if 10 clients are rate-limited at the same moment, they all back off for exactly 300 seconds and attack the server again in a synchronized wave. Adding randomized jitter desynchronizes the retries across a wide time window, allowing the server to recover smoothly.
