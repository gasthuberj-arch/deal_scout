Production Post-Mortems • Lesson 0015

SQLite B-Tree Index Traps & Zero-Miss In-Place ETS Cache Refresh

How an unindexed OR clause, missing partial indexes, and evict-on-write ETS invalidation caused full-table scans and cold-cache misses.

Tied to Your Mission

In commit 8baf24d, we fixed two subtle performance bugs that made DealScout feel sluggish under load: our analytics queries were silently performing full-table scans on deals, and our DealScout.Deals.StreamCache was deleting ETS cache entries every time a new Deal arrived—forcing concurrent LiveView visitors to hit a cold cache. Worse, our selective invalidation forgot that feed keys could be integers, strings, or slugs!

1. Trap #1: Disjunction (`OR`) Across an Unindexed Column

In DealScout.Analytics, we computed 24-hour and 1-hour deal velocity using this Ecto query:

# ❌ BEFORE: `inserted_at` has no index!
from d in Deal,
  where: d.published_at >= ^since_24h or d.inserted_at >= ^since_24h,
  select: count(d.id)

The deals table had an index on published_at, so why did SQLite scan the entire table? Because of the OR d.inserted_at >= ^since_24h predicate! When a WHERE clause combines two columns with OR and one of those columns (inserted_at) has no index, the query planner cannot satisfy the disjunction via the B-Tree index—it must inspect every row in the table to check whether inserted_at >= ^since_24h.

Since Deal ingestion always populates published_at (defaulting to DateTime.utc_now() when a feed omits it), checking or d.inserted_at >= ... was completely redundant. Removing it turned a full-table scan into an instant B-Tree index range count.

2. Trap #2: Sparse Nullable Columns Without Partial Indexes

Our analytics dashboard also counts cross-border deals (country IS NOT NULL) and foreign-keyboard warnings (keyboard_warning IS NOT NULL). Only a small minority of deals have non-null values in these columns, yet counting them required scanning every row in deals.

In migration 20261031215949_add_analytics_partial_indexes_to_deals.exs, we added SQLite Partial Indexes:

# ✅ Partial indexes only store rows where the column is NOT NULL:
create_if_not_exists index(:deals, [:country],
  where: "country IS NOT NULL",
  name: :deals_country_not_null_index
)

create_if_not_exists index(:deals, [:keyboard_warning],
  where: "keyboard_warning IS NOT NULL",
  name: :deals_keyboard_warning_not_null_index
)

Because a partial index omits all NULL rows, it takes almost zero disk space and zero write overhead on normal domestic deals, while making WHERE country IS NOT NULL counts instant index-only scans.

3. Trap #3: Evict-on-Write ETS Storms & Key Alias Mismatches

Look at what DealScout.Deals.broadcast_deal/1 and DealScout.Deals.StreamCache originally did whenever a new Deal was ingested:

# ❌ BEFORE:
# 1. Tiny 5-second TTL (@default_ttl_ms 5_000) meant idle feeds expired constantly.
# 2. On every new deal, we DELETED the ETS keys (`invalidate(feed_id: deal.feed_id)`):
if feed_id do
  :ets.match_delete(@table, {{:deals, feed_id, :_, :_, :_, :_, :_}, :_, :_})
  :ets.match_delete(@table, {{:deals, "all", :_, :_, :_, :_, :_}, :_, :_})
end

Two things went wrong here:

  1. Cold Cache Misses on Write: Deleting the ETS entry meant the next user loading the home page or switching tabs had to wait for a synchronous SQLite query. Similarly, in DealScout.Analytics.Server.init/1, deferring the initial warm via handle_continue(:initial_warm, state) without first seeding an empty snapshot meant early web requests during boot saw an empty ETS table and ran synchronous full-table scans on the request path!
  2. Incomplete Key Invalidation: Callers pass feed: to Deals.list_deals/1 as an integer ID (10), a URL param string ("10"), or a feed slug ("mydealz"). Only matching integer feed_id and "all" left cached entries under "10" and "mydealz" stale!

The Fix: In-Place `StreamCache.refresh/3` & Boot Seeding

Instead of evicting keys, StreamCache.refresh/3 finds all currently cached keys matching ["all", feed_id, to_string(feed_id), feed_slug], recomputes their queries in the background poller process, and overwrites them atomically via :ets.insert/2 with a 300-second TTL. Concurrent LiveView readers never experience a cache miss.
