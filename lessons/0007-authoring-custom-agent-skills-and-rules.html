Agent Craft • Lesson 0007

Authoring Custom Agent Skills & Rules

How to write predictable, high-leverage instructions, skills, and rules that shape agent behavior.

Transitioning to Agent Crafting

Now that you've used skills like teach, codebase-design, tdd, diagnosing-bugs, and code-review, how are these tools actually built? This lesson introduces the authoring levers from writing-for-agents and agy-customizations.

1. The Two Budgets: Context Load vs. Cognitive Load

Every line of instruction you create spends one of two finite budgets:

  • Context Load: The token and attention cost on the model's active window. Always-loaded rules (like AGENTS.md) spend context on every single turn, whether they fire or not.
  • Cognitive Load: The mental burden on the human to remember that a skill exists and type its slash command.

2. Invocation: Model-Invoked vs. User-Invoked

In Antigravity, every skill in .agents/skills/<name>/SKILL.md trades between these two loads:

  • Model-Invoked (Default): Its description acts as an active context pointer loaded into the agent's window. The agent can trigger the skill autonomously whenever relevant.
  • User-Invoked (disable-model-invocation: true): The description is stripped from the model's window, costing zero context load. Only the human typing its command (e.g. /teach) can trigger it.

3. The Writing Levers

Writing for an LLM is different from writing for humans. Use these three key levers:

  1. Leading Words: Choose compact terms rich in pretrained priors (tight, red, tracer bullet, relentless). Repeating a leading word anchors complex behaviors in a single token instead of paragraphs of explanation.
  2. Prompt the Positive: Telling a model "Do not use mock libraries" activates the concept of mock libraries in its attention weights (the "don't think of an elephant" trap). Instead, prompt the positive: "Use real in-memory adapters and public interfaces."
  3. Exhaustive Completion Criteria: Avoid fuzzy bounds like "review the code carefully." Use crisp, checkable bounds: "every modified struct has a test asserting observable output."
