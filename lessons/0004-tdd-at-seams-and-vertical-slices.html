Engineering • Lesson 0004

TDD at Seams & Vertical Slices

How to write durable tests that survive refactoring and drive features via tracer bullets.

Transitioning to the Engineering Loop

Now that you know where architectural seams belong (Lesson 0002), this lesson shows you how to test across those seams using Test-Driven Development (TDD) without creating brittle, implementation-coupled test suites.

1. The Anatomy of a Good Test

Tests must verify observable behavior through public interfaces, never private implementation details. A test should read like a specification of system capability:

# GOOD: Verifies observable outcome through the public seam
test "ingest_feed/2 parses valid feeds and stores deals", %{source: source} do
  feed_xml = fixture("sample_feed.xml")
  
  assert {:ok, count} = Deals.ingest_feed(source, feed_xml)
  assert count == 3
  assert Deals.list_deals_for_source(source.id) |> length() == 3
end

# BAD: Implementation-coupled spy test
test "ingest_feed/2 calls internal parser and repo" do
  # Mocks internal helper and asserts on private calls
  expect(FeedParser, :parse, fn _ -> {:ok, []} end)
  expect(Repo, :insert_all, fn _ -> {0, nil} end)
  
  Deals.ingest_feed(:mock_source, "xml")
end

The good test survives when you replace FeedParser with a streaming XML parser. The bad test breaks the moment you touch an internal function name, even when the feature works perfectly.

2. Beware the Three Fatal Anti-Patterns

  1. Implementation Coupling: Mocking internal functions or checking intermediate database tables. The tell: your test breaks when you refactor even though user-observable behavior didn't change.
  2. Tautological Tests: The test assertion calculates the expected result with the exact same logic as the production code (e.g. expected = Enum.sum(items)). The test passes by construction and cannot catch logic flaws. Expected values must come from independent literal sources or worked examples.
  3. Horizontal Slicing: Writing 10 speculative test cases upfront before writing code. You end up asserting on imagined structures rather than real capabilities.

3. Vertical Slicing (Tracer Bullets)

Instead of horizontal test dumping, work in vertical slices:

One test → One minimal implementation → Repeat.

Each test acts as a tracer bullet through the entire stack, teaching you about the real interface and allowing you to adjust before committing to the next step.
