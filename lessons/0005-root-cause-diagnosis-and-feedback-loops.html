Root-Cause Diagnosis & Feedback Loops

The scientific method for squashing elusive bugs and performance regressions without guessing.

Closing the Practical Engineering Loop

In Lesson 0004, you learned to drive features forward with TDD at seams. But when something breaks in production or tests flake, guessing and adding random print statements wastes hours. This lesson introduces the rigorous, scientific debugging discipline from diagnosing-bugs.

1. The Cardinal Creed: Building the Loop IS the Skill

Most developers fail at debugging because they stare at code and leap straight into guessing theories. In our system:

Building the feedback loop IS the skill. Everything else is mechanical.

If you have a tight, repeatable signal (a test, a curl command, a CLI script) that fails predictably on the bug and takes under 3 seconds to run, finding the root cause is straightforward. If you don't have one, no amount of guessing will save you.

2. Phase 1: The Four Rules of a Valid Loop

Before writing a single hypothesis, Phase 1 requires you to name one runnable command that is:

  1. Red-capable: Drives the actual code path and asserts the user's exact symptom (not just "didn't crash").
  2. Deterministic: Consistent outcome on every execution (or pinned to a high repro rate for race conditions).
  3. Fast: Takes seconds, not minutes.
  4. Agent-runnable: Executes unattended in terminal or test runner.

3. Phase 2 & 3: Minimize and Hypothesize

  • Minimize (Phase 2): Strip inputs, configurations, and steps one by one. You are done minimizing when every remaining element is load-bearing—removing any single item makes the reproduction go green. A minimal repro drastically narrows the suspect space.
  • Hypothesize (Phase 3): Formulate 3–5 ranked, falsifiable hypotheses before testing. Avoid anchoring on your first hunch. Every hypothesis must state a testable prediction: "If X is the cause, then changing Y makes it disappear."

4. Phase 4: Clean Instrumentation

When probing with logs, never sprinkle generic IO.puts across twenty files. Tag every debug statement with a unique ID (e.g. [DEBUG-7f2a]). When the bug is fixed, a single grep command cleanly eliminates 100% of temporary probe code.

5. Check Your Understanding

Test your grasp of scientific diagnosis with these retrieval checks. Feedback is immediate.

⚡ Quick Knowledge Check
1. What must be established before hypothesizing about bug causes?
2. When is the bug reproduction scenario considered fully minimized?
3. Why should all temporary debug logs carry unique tags?
