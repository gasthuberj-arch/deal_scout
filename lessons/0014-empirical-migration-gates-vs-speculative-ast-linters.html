Empirical Migration Gates vs. Speculative AST Linters

Why we wrote—and 5 minutes later deleted—a 130-line Elixir AST migration linter in favor of a seeded N-1 → N WAL budget test.

Tied to Your Mission

Right after fixing the FTS5 migration trigger bug in commit a293663, we over-reacted by writing a 130-line static AST + regex SQL linter in test/deal_scout/repo_migration_test.exs—and even edited an old historical migration from two weeks ago just to make the linter pass. Five minutes later, in commit b03d524, we deleted the entire AST linter. This lesson examines why static regex linting of SQL migrations violates our testing philosophy (avoiding Implementation Coupling and Speculative Generality) and how an empirical outcome gate catches the real bug in 30 lines.

1. The Over-Correction: Writing a 130-Line Speculative AST Linter

When a bug slips through, it is tempting to write a static source-code rule against the exact syntax of the bug. In commit a293663, we added lint_migration_ast!/3 to walk every migration's Elixir AST with Macro.prewalk/2 and run regular expressions against raw SQL strings:

# ❌ WHAT WE WROTE IN a293663 (AND DELETED IN b03d524):
if Regex.match?(~r/CREATE\s+TRIGGER\b.*\bAFTER\s+UPDATE\s+ON\b/s, normalized) do
  flunk("Migration creates an unscoped AFTER UPDATE ON trigger...")
end

# Counting line numbers of regex matches to guess whether UPDATE ran before DROP TRIGGER:
if first_bulk_mutation_line < last_drop_trigger_line do
  flunk("Migration runs a bulk UPDATE/DELETE on `deals` before `DROP TRIGGER`...")
end

Why was this a mistake across multiple axes?

  • Implementation Coupling: It tested how migration code was spelled (exact regexes on table names like DEALS and SQL keywords) rather than what the migration actually did to the database.
  • Speculative Generality: Over 130 lines of AST walking and escape-hatch comments (# migration-lint: allow-table-rewrite) were added to guard hypothetical future syntax patterns that had never occurred.
  • Blind to Real Database Semantics: A regex on a single migration file has no idea what triggers previous migrations left behind in the database! Even if the latest migration never mentions DROP TRIGGER at all, an existing trigger from migration N-5 can still fire on a bulk UPDATE in migration N.

2. The Cardinal Sin: Editing Historical Migrations

Because the AST linter scanned all migration files in priv/repo/migrations/, it immediately failed on 20261020133300_add_deals_fts.exs—a historical migration that had already run in production weeks earlier. To appease our own linter, we edited that historical migration in a293663.

Never edit historical migrations that have already run in production (unless fixing a literal syntax error that prevents fresh DB setup). Ecto tracks executed migrations in the schema_migrations table by version timestamp. Production will never re-run 20261020133300, which means editing it causes fresh test databases and production databases to diverge silently.

3. The Fix (`b03d524`): An Empirical N-1 → N WAL & Runtime Gate

In commit b03d524, we reverted the historical migration edit, deleted all 130 lines of AST/regex linting, and kept only the observable outcome test at the database Seam:

# ✅ TEST THE OUTCOME AT THE SEAM (test/deal_scout/repo_migration_test.exs):
# 1. Migrate up to N - 1 (simulating production state prior to latest migration)
Ecto.Migrator.run(repo, migrations_path, :up, to: prior_version, log: false)

# 2. Seed 1,000 realistic deals (~2.5 KB description + clean_text each) via recursive CTE
seed_deals_for_migration_benchmark(repo)

# 3. Truncate the WAL so we measure ONLY the latest migration's footprint
Ecto.Adapters.SQL.query!(repo, "PRAGMA wal_checkpoint(TRUNCATE);", [])

# 4. Run latest migration N and assert runtime and WAL size budgets
{duration_us, [^latest_version]} =
  :timer.tc(fn ->
    Ecto.Migrator.run(repo, migrations_path, :up, all: true, log: false)
  end)

assert div(duration_us, 1000) < 750
assert wal_bytes < 12 * 1024 * 1024

Notice the leverage: whether a future migration causes runaway WAL growth via an unscoped trigger from 10 migrations ago, an accidental 12-step table copy, or a slow correlated subquery, this 30-line empirical gate catches it automatically—with zero regexes and zero false positives.
