SQLite Storage Bloat, External-Content FTS5, & Trigger WAL Amplification

How triple text storage, unscoped update triggers, and RAM-backed /tmp snapshots blew up our SQLite footprint—and how we fixed them.

Tied to Your Mission

In commits 0622c75 and a293663, we discovered three compounding SQLite storage and operational mistakes in DealScout: our database was storing deal text three times, our migration to clean it up accidentally triggered row-by-row FTS5 rebuilds before dropping the FTS table, and our hot backup snapshots were writing to RAM-backed /tmp. This lesson dissects each mistake so you can spot storage and migration traps before shipping.

1. Mistake #1: Triple Text Storage with Default FTS5

During Deal ingestion (DealScout.Deals.Ingestion), RSS items arrive with verbose raw HTML in description. Our parser strips tags and extracts structured metadata into clean_text, yet we still persisted both description and clean_text in the deals table.

Worse, our original full-text search index used a standard SQLite FTS5 virtual table:

-- ❌ BEFORE: Default FTS5 creates an internal `deals_fts_content` shadow table
-- that stores a FULL second copy of title, clean_text, and merchant!
CREATE VIRTUAL TABLE deals_fts USING fts5(
  title,
  clean_text,
  merchant,
  tokenize='unicode61 remove_diacritics 2'
);

Because default FTS5 stores its own copy of every indexed column inside a hidden deals_fts_content shadow table, every Deal stored its text three times on disk: once in deals.description, once in deals.clean_text, and once in deals_fts_content.

The Fix: External-Content FTS5 (`content='deals'`)

By declaring content='deals' and content_rowid='id' (and setting description: nil after extracting clean_text), FTS5 stores only the compact inverted token index and reads column values directly from deals when needed:

-- ✅ AFTER: External-content FTS5 stores zero duplicate text rows
CREATE VIRTUAL TABLE deals_fts USING fts5(
  title,
  clean_text,
  merchant,
  content='deals',
  content_rowid='id',
  tokenize='unicode61 remove_diacritics 2'
);

This shrank per-deal storage enough to expand default retention in DealScout.Maintenance.Pruner from 30 days to 365 days while keeping the database smaller than before.

2. Mistake #2: Unscoped Update Triggers & Migration Ordering

When we wrote migration 20261031221746_optimize_deal_storage_and_external_fts.exs to null out legacy description HTML and rebuild deals_fts, we initially ordered the statements like this:

# ❌ WRONG ORDER: Updating `deals` while `deals_au` trigger is still active!
execute("UPDATE deals SET description = NULL WHERE description IS NOT NULL;")

execute("DROP TRIGGER IF EXISTS deals_ai;")
execute("DROP TRIGGER IF EXISTS deals_ad;")
execute("DROP TRIGGER IF EXISTS deals_au;")
execute("DROP TABLE IF EXISTS deals_fts;")

Why was this disastrous? Look at how the legacy deals_au trigger was defined:

-- ❌ Unscoped AFTER UPDATE ON fires on ANY column change (even `description` or `temperature`!)
CREATE TRIGGER deals_au AFTER UPDATE ON deals BEGIN
  DELETE FROM deals_fts WHERE rowid = old.id;
  INSERT INTO deals_fts(rowid, title, clean_text, merchant) ...
END;

Because deals_au lacked an OF col1, col2 column list, running UPDATE deals SET description = NULL fired the FTS delete+insert trigger for every single row in the database—re-indexing title, clean_text, and merchant into a deals_fts table that we dropped four lines later! That doubled migration runtime and bloated the .db-wal file.

The Two-Part Fix

  1. Drop triggers before bulk mutations: Always execute DROP TRIGGER (and DROP TABLE deals_fts) before running a bulk UPDATE or DELETE on the parent table.
  2. Scope update triggers to indexed columns (SQLite CREATE TRIGGER): Use AFTER UPDATE OF title, clean_text, merchant ON deals so updating unrelated columns (like description, temperature, or canonical_deal_id) never fires FTS maintenance.

3. Mistake #3: Cross-Filesystem `/tmp` Snapshots (`VACUUM INTO`)

In DealScout.Backup.create_sqlite_snapshot/1 (part of Replica sync), we use SQLite's atomic VACUUM INTO command to create a clean snapshot file. Previously, it defaulted to System.tmp_dir!() (/tmp).

On container platforms like Fly.io, /tmp resides on the ephemeral root filesystem or a RAM-backed tmpfs, whereas the SQLite database lives on a persistent NVMe volume mounted at /data. Writing a multi-hundred-megabyte snapshot into /tmp risks exhausting container memory/swap. We fixed config/runtime.exs so production snapshots write to Path.dirname(DATABASE_PATH) on the persistent /data volume.
