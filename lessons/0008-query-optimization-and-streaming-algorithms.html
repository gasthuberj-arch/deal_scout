Engineering • Lesson 0008

Query Optimization & Streaming Algorithms

What DealScout teaches about percolation search, composite indexes, thundering herds, and LiveView lifecycles.

Tied to Your Mission

Building DealScout exposed a unique set of real-time engineering bottlenecks: streaming thousands of live deals against thousands of standing alert rules. In this lesson, we break down the core algorithmic paradigms and database patterns discovered and refined throughout this codebase.

1. The Core Paradigm: Percolation vs. Traditional Search

Most web applications solve traditional search: one incoming query evaluated against millions of indexed documents. You build an inverted index (e.g. Postgres GIN or Elasticsearch) and look up documents matching the search keywords.

A real-time notification engine like DealScout flips this problem upside down. This is the Percolation Problem (also called Reverse Search):

  • You have thousands of standing rules (user alerts with positive keywords, negative exclusions, and price caps).
  • You have a continuous stream of new documents arriving one-by-one or in batches.
TRADITIONAL SEARCH (1 Query vs. N Docs)
┌────────────────┐      ┌──────────────────────────────┐
│  Search Query  │ ───► │  Inverted Index (100k Deals) │ ───► Top Results
└────────────────┘      └──────────────────────────────┘

PERCOLATION / REVERSE SEARCH (1 Doc vs. N Queries)
┌────────────────┐      ┌──────────────────────────────┐
│  Incoming Deal │ ───► │ 10,000 Standing Alert Rules  │ ───► Matched Users
└────────────────┘      └──────────────────────────────┘

A naive solution iterates over all $N$ rules for every incoming deal: running regexes or string operations across the deal's text. At 5,000 rules and 1,000 deals, that is 5,000,000 evaluations per ingestion cycle, which quickly exhausts CPU.

How DealScout Solved It: Aho-Corasick + Inverted Rule Map

In DealScout.KeywordEngine, DealScout compiles all literal tokens from active alert rules into an Erlang :binary.compile_pattern/1 (an Aho-Corasick automaton) and stores an inverted token-to-rule map in :persistent_term.

  1. Single-Pass Text Scan: An incoming deal's title and description are scanned in a single pass ($O(\text{text length})$), identifying all matching tokens simultaneously.
  2. Candidate Rule Filtering: The matched tokens look up candidate rules in the inverted index. Rules whose required keywords never appeared are pruned instantly without running any Elixir logic.
  3. Cost-Bounded Detailed Evaluation: Only candidate rules are evaluated for price bounds, dropshipper exclusions, and boolean negation, wrapped inside a ComputeGuard budget.

2. Database Indexing: The Composite Stream Pattern

During the optimization of DealScout's deal feed, a critical database bottleneck appeared: single-column indexes on canonical_deal_id misled the query planner into performing full table scans and expensive external sorts when running queries such as:

SELECT * FROM deals
WHERE canonical_deal_id IS NOT NULL
ORDER BY published_at DESC, id DESC
LIMIT 50;

When an index only covers canonical_deal_id, the database must retrieve every matching row pointer, fetch the table pages, and sort all matching records in working memory. When the table grows into tens of thousands of rows, query latency spikes.

The Fix: Composite Index Matching Sort Order

create index(:deals, [:canonical_deal_id, :published_at, :id])
create index(:deals, [:feed_id, :canonical_deal_id, :published_at, :id])

By defining the composite index to include both the filter predicate and the ORDER BY columns in exact sequence, Postgres and SQLite can perform a pure index-ordered backward/forward scan. The database walks the B-tree leaf nodes and halts immediately after 50 rows. Sorting time drops to zero milliseconds.

3. The LiveView Dual-Mount Trap

Phoenix LiveView's architecture provides instant SEO rendering followed by real-time WebSocket enhancement. However, this creates a classic query multiplication hazard:

  • Initial HTTP Request: LiveView invokes mount/3 and renders a static HTML response.
  • WebSocket Connection: The client browser establishes a WebSocket. LiveView invokes mount/3 a second time in the stateful process.
  • Route Navigation: LiveView immediately executes handle_params/3 after mount.

If your mount/3 calls load_matches() or load_deals(), you execute the database query twice on page load. If handle_params/3 also executes the load, you run it three times per user visit.

The Pattern: Lazy Streams in Mount

DealScout fixed this in DealLive.Index and MatchLive.Index by initializing streams empty in mount/3 (stream(socket, :deals, [])) and deferring database queries strictly to handle_params/3, cutting database queries per page load in half.

4. Cache Stampedes and Background Warmers

Heavy analytic aggregations (deal volumes, discount distributions, merchant trust metrics) cannot run on every page visit without overloading the database. Caching results in ETS with a Time-To-Live (TTL) is standard practice, but introduces a failure mode under load:

The Thundering Herd (Cache Stampede): The moment a popular cached key expires, 30 concurrent user requests miss the cache at the exact same millisecond. All 30 processes simultaneously initiate the expensive aggregation query, causing CPU spikes and database pool exhaustion.

DealScout solved this by decoupling cache reads from cache writes via DealScout.Analytics.Warmer: an active background GenServer that periodically recalculates analytics and updates ETS ahead of schedule. Incoming web requests only ever read from ETS, guaranteeing sub-millisecond responses and zero stampedes.

5. Real-World Dirty Data & Filter Semantics

When parsing external RSS and JSON feeds, DealScout encountered dirty real-world data:

  • Locale Number Formats: European thousand separators and commas (e.g., 1.299,00 € vs. $1,299.00) crash standard float parsers.
  • The Nil-Price Semantic Trap: When a user creates an alert with max_price: 50.00, how should a deal with price: nil be handled? If nil is coerced or ignored, the user receives alerts for products without prices. DealScout enforces strict filtering: not is_nil(deal.price) and deal.price <= rule.max_price.
