Database Architecture • Lesson 0014

The Traps of "Fast Local SQL": Missing Indexes & Migration Cascades

Why embedded databases lull us into false bets, and how to tame trigger cascades, full-table scans, and migration lockups.

Tied to Your Mission

Because SQLite is embedded and runs directly in-process with zero network round-trip latency, small datasets create the illusion of infinite speed. This fosters dangerous architectural bets: that unindexed filter scans don't matter, that bulk updates in migrations are lightweight, and that triggers are free. In production DealScout, these bets caused full-table scan thrashing on analytics dashboards and multi-minute migration freezes. This lesson unpacks the exact failure modes and the physical database principles that solve them.

1. The Missing Partial Index & The `OR` Anti-Pattern

The Bet: "We only have a few tens of thousands of deals. An in-memory scan over local NVMe is so fast we don't need dedicated indexes for analytics queries."

In DealScout's analytics dashboard, we tracked country-specific imports and foreign keyboard warnings with queries like:

# The unindexed queries in DealScout.Analytics:
from d in Deal, where: not is_nil(d.country), select: count(d.id)
from d in Deal, where: not is_nil(d.keyboard_warning), select: count(d.id)

Out of 20,000 deals, perhaps only 500 have a country set, and only 80 have a keyboard_warning. Yet without an index, SQLite had to execute a full-table scan across all 20,000 rows. Every time a background poller ingested a deal or an admin opened the dashboard, SQLite swept through every page on disk, loading pages into the pager cache and displacing active LiveView data.

To compound the problem, the 24-hour activity query included an OR condition:

# The OR trap:
where: d.published_at >= ^since_24h or d.inserted_at >= ^since_24h

In relational databases, an index on published_at cannot satisfy an OR across a separate column (inserted_at) without an expensive index-merge or falling back to a full-table scan. By removing the redundant fallback and creating partial indexes, the performance profile changed dramatically:

# In priv/repo/migrations/..._add_analytics_partial_indexes_to_deals.exs:
create index(:deals, [:country],
  where: "country IS NOT NULL",
  name: :deals_country_not_null_index
)

create index(:deals, [:keyboard_warning],
  where: "keyboard_warning IS NOT NULL",
  name: :deals_keyboard_warning_not_null_index
)

The Enduring Principle: Index the exception, not the rule. A partial index (WHERE column IS NOT NULL) only stores B-tree entries for rows where the condition holds. For sparse flags (warnings, errors, country tags), a partial index takes mere kilobytes of disk space, remains hot in cache, and turns a 20,000-row table scan into a microscopic B-tree index leaf count.

2. The Migration Trigger Cascade (The "Free" UPDATE Trap)

The Bet: "Clearing out unused column data during a migration is a simple UPDATE deals SET description = NULL statement that finishes in milliseconds."

When optimizing deal storage, DealScout transitioned from storing raw HTML descriptions to clean parsed text. The migration included this innocent line:

execute("UPDATE deals SET description = NULL WHERE description IS NOT NULL;")

In production or on a populated database, this single line took tens of seconds to minutes, locking the database, ballooning the WAL log, and risking deploy timeouts. Why?

Earlier migrations had created full-text search triggers:

CREATE TRIGGER deals_au AFTER UPDATE ON deals BEGIN
  DELETE FROM deals_fts WHERE rowid = old.id;
  INSERT INTO deals_fts(rowid, title, clean_text, merchant)
  VALUES (new.id, new.title, new.clean_text, new.merchant);
END;

Notice the flaw: the trigger was unscoped (AFTER UPDATE ON deals). It listened to updates on any column in deals, including description! When the migration ran UPDATE deals SET description = NULL on 10,000 deals, SQLite fired the trigger 10,000 individual times:

UPDATE deals SET description = NULL
 ├── Row 1  ──► Fire deals_au ──► DELETE FROM deals_fts ──► INSERT INTO deals_fts (B-tree re-balance)
 ├── Row 2  ──► Fire deals_au ──► DELETE FROM deals_fts ──► INSERT INTO deals_fts (B-tree re-balance)
 ├── Row 3  ──► Fire deals_au ──► DELETE FROM deals_fts ──► INSERT INTO deals_fts (B-tree re-balance)
 └── ... 10,000 times! (Gigabytes of WAL writes, index thrashing, lock contention)

Each row-by-row FTS update modifies multiple hidden shadow tables (deals_fts_idx, deals_fts_data, deals_fts_docsize). The database spent 99.9% of its time re-indexing the exact same text that hadn't even changed!

The Resolution: Two fundamental migration rules:

  1. Drop Triggers Before Bulk Mutations: Always drop triggers before running bulk data cleanup, and rebuild the index once at the end: 
    # Correct migration order:
execute("DROP TRIGGER IF EXISTS deals_au;")
execute("DROP TABLE IF EXISTS deals_fts;")
execute("UPDATE deals SET description = NULL WHERE description IS NOT NULL;")
# Recreate external FTS and populate in ONE bulk operation:
execute("INSERT INTO deals_fts(deals_fts) VALUES('rebuild');")
  2. Column-Scoped Triggers: Never use naked AFTER UPDATE ON table. Always scope to the specific columns that affect the index: 
    CREATE TRIGGER deals_au AFTER UPDATE OF title, clean_text, merchant ON deals BEGIN ...
    Now updates to temperature, description, or canonical_deal_id never touch FTS5.

3. External-Content FTS5: Eliminating Shadow Duplication

The Bet: "FTS5 is just an index on our table."

By default, a standard FTS5 virtual table stores a complete, uncompressed duplicate copy of all indexed text in a hidden shadow table (deals_fts_content). If your deals table contains 50 MB of titles and descriptions, deals_fts_content stores another 50 MB, doubling disk usage and memory churn.

By specifying content='deals' and content_rowid='id', SQLite creates an external-content table:

CREATE VIRTUAL TABLE deals_fts USING fts5(
  title,
  clean_text,
  merchant,
  content='deals',
  content_rowid='id',
  tokenize='unicode61 remove_diacritics 2'
);

In external-content mode, SQLite stores only the inverted token index and token offsets. When a search query matches, SQLite fetches the original row text directly from the underlying deals table. This cut DealScout's full-text search disk footprint by more than 60%.

4. The Verification Gate: The Seeded N-1 WAL Gate

How do we ensure that a future developer or AI agent never introduces a slow migration or forgotten trigger? In DealScout, we instituted a migration test in test/deal_scout/repo_migration_test.exs:

# 1. Run migrations up to N - 1
for v <- prior_versions do
  Ecto.Migrator.up(repo, v, load_migration_module(migrations_path, v))
end

# 2. Seed 1,000 realistic records with large text payloads
seed_deals_for_migration_benchmark(repo, 1_000)

# 3. Execute latest migration N and assert strict budgets:
{time_us, _} = :timer.tc(fn ->
  Ecto.Migrator.up(repo, latest_version, load_migration_module(migrations_path, latest_version))
end)

assert time_us < 2_000_000, "Migration exceeded 2.0s time budget!"
assert wal_size < 10_000_000, "Migration generated excessive WAL churn!"

If a migration accidentally triggers row-by-row trigger cascades or full table rewrites, the seeded test fails immediately in CI before the migration can ever hit production.
