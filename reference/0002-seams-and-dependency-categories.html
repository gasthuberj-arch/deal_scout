Heuristics for positioning seams, choosing adapters, and testing interfaces cleanly.

The Seam Concept

Defined by Michael Feathers (Working Effectively with Legacy Code):

Seam: A place where you can alter behavior without editing in that place; the exact location where a module's interface lives.

The Four Dependency Categories

Category Characteristics Seam Strategy Testing Approach
1. In-process Pure computation, data transformation, internal memory. No I/O. No seam needed. Merge directly into the deep module. Test directly through the module's interface.
2. Local-substitutable Persistent or stateful dependencies with local test doubles (e.g. SQLite, ETS). Internal seam only. Stand-in stays inside module boundary. Run fast in-memory stand-in within test suite.
3. Remote Owned Services you own across a network boundary (internal microservices, RPC). Port at the seam. External interface accepts adapter. HTTP adapter in production; in-memory adapter in test.
4. True External Third-party APIs outside your control (Stripe, Twilio, SendGrid). Injected port. Strict boundary to protect your domain. Mock adapter satisfying the port contract in test.

Seam Discipline

  • The Two-Adapter Rule: One adapter means a hypothetical seam. Two adapters means a real one. Never introduce interface indirection unless at least two adapters are actively justified (e.g., Production HTTP + In-memory test fake).
  • Internal vs. External Seams: Private seams used internally for unit isolation must never be leaked across the module's public interface.
  • Replace, Don't Layer: When deepening a module, delete old unit tests for deprecated internal parts. Test exclusively against the external interface.
