Good Tests vs. Bad Tests

Dimension Good Test (Behavioral) Bad Test (Implementation-Coupled)
Test Surface Crosses public seam; uses caller interface Calls private methods or spies on internals
Assertion Target Observable outcome (state change, return value) Call counts (expect(mock).toHaveBeenCalled())
Expected Values Independent literal or worked example from spec Recomputed with the same logic as the code
Refactoring Resilience Survives full internal restructuring unscathed Breaks whenever private functions or names change

The Three Fatal Test Anti-Patterns

1. Implementation-Coupled Tests

Mocks internal collaborators, spies on private functions, or verifies via database side-channels instead of public APIs. The tell: the test breaks during a refactor even though user-observable behavior never changed.

2. Tautological Tests

The test assertion recomputes expected output using the exact same formula or helper the production code uses (e.g. assert total == items.reduce(...)). It passes by construction and can never catch real calculation bugs.

3. Horizontal Slicing

Writing 15 speculative test cases upfront before writing any code. Slicing horizontally commits to rigid, imagined interfaces. The fix: Use vertical slicing (tracer bullets): write one failing test → implement minimal passing code → repeat.

The Rules of the Red-Green Loop

  1. Red before Green: Always see the test fail before making it pass.
  2. Minimal Code: Write only enough production code to turn the test green. Don't anticipate future steps.
  3. One Slice at a Time: One seam, one test, one minimal implementation per cycle.
  4. Separate Refactoring: Keep refactoring in the review phase, not inside the red-green loop.
